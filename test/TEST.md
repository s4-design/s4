# Тестирование S4

## Структура

```
test/
├── TEST.md               ← этот файл
├── snapshot.mjs           ← скрипт тестов и утверждения эталонов
├── index.html             ← страница со всеми элементами S4
├── icons/                 ← иконки для тестовой страницы
├── images/                ← прочее (например, логотип)
├── __snapshots__/         ← локальные эталоны (в .gitignore)
│   ├── light/             ←   для [preset=light]
│   └── dark/              ←   для [preset=dark]
└── __diff__/              ← снимки для проверки (в .gitignore, очищается при каждом запуске)
    ├── light/
    │   ├── {id}.expected.png  ← эталон
    │   ├── {id}.actual.png    ← текущий рендер
    │   └── {id}.diff.png      ← маска различий
    └── dark/
```

После свежего клонирования папок `__snapshots__/` и `__diff__/` нет - они появляются при запуске тестов. Эталоны создаются только после подтверждения (`pnpm test-approve`).

## Автоматические тесты (скриншотные снэпшоты)

Playwright открывает `test/index.html` в headless-браузере, скриншотит каждую `<section id="...">` и сравнивает с локальным эталоном.

### Запуск

```bash
pnpm test                   # сравнить с эталонами
pnpm test-approve           # утвердить снимки из __diff__ и очистить её
```

Скрипт сам поднимает встроенный статический сервер (без внешних зависимостей), не нужно ничего запускать отдельно.

### Первый запуск

Эталоны в Git не хранятся: у каждого свои, снятые на его машине. После свежего клонирования `__snapshots__/` пуста: первый `pnpm test` не создаёт эталоны, а складывает все снимки в `__diff__/` как `{id}.actual.png` со статусом `NEW` и завершается ошибкой. Проверьте снимки и выполните `pnpm test-approve` - он скопирует их в `__snapshots__/` и очистит `__diff__/`. Следующий `pnpm test` пройдёт.

Эталоны из другого окружения (другая ОС, другой браузер) для сравнения не подходят. Это ожидаемо: эталон фиксирует рендер конкретной машины, переносить его между машинами не нужно.

### Что проверяется

Для каждого пресета (`light`, `dark`) проход по всем `<section id="...">` из `index.html`:
- список секций парсится из разметки автоматически - новые секции попадают в тест сами;
- для `[preset=light]` и `[preset=dark]` снимаются скриншоты каждой секции;
- Итого: N секций × 2 пресета скриншотов.

Секции длиннее вьюпорта снимаются целиком, в кадр попадает всё, что их перекрывает.

### Исключение из снимков

Перед съёмкой скрипт добавляет стиль `.no-snapshot { display: none !important; }` (в `snapshot.mjs`). Любой элемент с этим классом скрывается и не попадает в кадр.

Так исключают то, что не имеет смысла фиксировать в эталоне - плавающие панели, переключатели, кнопки поверх контента. Класс ставится прямо в `index.html`:

```html
<div class="no-snapshot display--inline-flex ... position--fixed ...">...</div>
```

Скрытая `<section id="...">` даёт `SKIP - not visible`. Старый PNG при этом не удаляется: файлы в `__snapshots__/` скрипт никогда не чистит, лишние надо убирать руками.

### Результат

```
=== Results: 80 passed, 0 failed, 0 new, 0 skipped (light: 40 snapshots, dark: 40 snapshots) ===
```

- `PASS` - совпало с эталоном
- `FAIL` - отличается; в `__diff__/{preset}/` сохранены `{id}.expected.png`, `{id}.actual.png` и `{id}.diff.png`
- `NEW` - эталона нет; сохранён только `{id}.actual.png`
- `SKIP` - элемент не найден или скрыт

При расхождении размеров маска не строится: в `__diff__/{preset}/` сохраняются только `expected` и `actual`, размеры выводятся в консоль.

`__diff__/` очищается в начале каждого запуска, поэтому старые снимки не накапливаются.

### Когда обновлять эталоны

1. `pnpm test` - сравнить и открыть `__diff__/`.
2. Если изменения ожидаемы - `pnpm test-approve`: проверенные `actual` станут эталонами, `__diff__/` очистится.
3. `pnpm test` - убедиться, что всё проходит.

Обновление локальное, эталоны в Git не коммитятся.

### Команды package.json

```json
"test": "node test/snapshot.mjs",
"test-approve": "node test/snapshot.mjs --approve"
```

## Ручной просмотр тестовой страницы

```bash
pnpx serve . -l 3001
# открыть http://localhost:3001/test/
```

Для визуальной проверки изменений, отладки, разработки новых вариаций элементов.
